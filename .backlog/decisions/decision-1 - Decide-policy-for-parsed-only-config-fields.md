## Context

`invo` currently accepts and deserializes several configuration fields that do not affect runtime behavior yet:

- `llm.providers[].model_path`
- `ignored_vendors`
- `actions`
- `processing`
- `logging`
- `output.include_hash`
- `output.schema_version`

This was intentionally documented after trimming the generated `config.yaml` to active settings only. The current compromise is:

- The starter config generated by `invo init` only includes settings that work today.
- The parser still accepts some future-facing fields so existing/user-authored configs do not fail immediately.
- `invo config doctor`, README, and `agent-context` identify these fields as parsed-only/future.

That compromise has short-term compatibility benefits, but it also creates product and maintenance risk:

1. Users may assume parsed config means implemented behavior.
2. Future fields must be tracked across `Config` structs, validation allowlists, schema output, docs, doctor warnings, and agent-context.
3. If parsed-only fields accumulate, the config surface becomes larger than the real product surface.
4. Agents and scripts need a reliable distinction between active configuration and aspirational configuration.

Related backlog items:

- TASK-25 — Reduce config validation drift risk
- TASK-28 — Add OCR fallback for scanned PDFs
- TASK-29 — Add parallel batch processing
- TASK-31 — Implement post-processing actions
- TASK-32 — Implement deduplication using file hashes

## Decision

Proposed policy:

1. **Default rule: do not add new parsed-only config fields.** New config keys should be accepted only when the runtime behavior is implemented in the same change.
2. **Existing parsed-only fields must be resolved deliberately.** Each current parsed-only field should either be implemented, removed from accepted config, or retained with an explicit compatibility reason.
3. **Generated config remains active-only.** `invo init` should continue to write only settings that affect current behavior.
4. **Every retained parsed-only field must be discoverable.** If a parsed-only field remains accepted, it must be listed consistently in:
   - README config status table
   - `invo config doctor`
   - `invo agent-context --json`
   - config schema descriptions where possible
5. **No silent behavior claims.** Docs and examples must never imply that parsed-only fields are active.

Recommended treatment of the current parsed-only fields:

| Field | Proposed direction | Rationale |
| ----- | ------------------ | --------- |
| `processing.ocr` | Implement via TASK-28 or remove | OCR is a clear user-visible feature and already reflected by `extraction.ocr_used`. |
| `processing.parallelism` | Implement via TASK-29 or remove | Batch performance is valuable, but the current serial behavior is explicitly documented. |
| `processing.deduplication` | Implement via TASK-32 or remove | Hashes already exist, but skip/report semantics need a product decision. |
| `actions` | Keep low priority; implement via TASK-31 or remove | Useful workflow feature, but broad and easy to overbuild. |
| `ignored_vendors` | Remove unless a concrete skip feature is planned | It is less valuable while extraction is user-invoked per file. |
| `logging` | Prefer remove | Runtime logging is already controlled by `-v/--verbose` and `RUST_LOG`; config logging adds complexity. |
| `output.include_hash` | Prefer remove or implement quickly | Output hash is currently always emitted; a toggle may weaken schema stability. |
| `output.schema_version` | Prefer defer until versioning exists | Schema versioning should be introduced with a real compatibility policy. |
| `llm.providers[].model_path` | Prefer remove unless local file-backed models are planned | Current providers use provider model names, not model file paths. |

## Consequences

Positive consequences:

- The config surface becomes more honest and easier to explain.
- Agents can trust that active config keys change runtime behavior.
- Future features will include implementation, docs, validation, and discovery in one coherent change.
- `config doctor` remains useful as a transition tool instead of becoming a permanent warning list.

Negative consequences / tradeoffs:

- Removing accepted parsed-only fields may break configs from early users who copied old examples or explored the schema.
- Implementing every retained field increases near-term work.
- A stricter policy makes speculative config design harder, but that is likely desirable for a CLI intended for scripts and agents.

Follow-up actions if accepted:

1. Audit each parsed-only field and create/remove implementation tasks as needed.
2. Update README, `config doctor`, `agent-context`, and JSON schema descriptions to match the accepted policy.
3. Add regression tests that fail if a parsed-only field is accidentally presented as active.
4. Close or revise feature tasks for parsed-only fields that are intentionally removed instead of implemented.
